# The dashboard

Back to the [README](../README.md). Which rows open and where every cell comes from is in [harness.md](harness.md); the job file in [jobs.md](jobs.md); commands in [cli.md](cli.md).

`cones tui` shows jobs, live sessions and runs on one screen. It reloads about every second, on a thread of its own so a slow transcript read never holds a keypress or the spinner, as [polling](#polling) describes, and reads `N working · N need input · N idle · N jobs · N runs` on its summary line. Stop and delete commands run in the background too, with their progress in the hint line: a confirmed delete removes the row at once, before `claude rm` returns, and a failed one puts it back with the error; the hint line names the session by its title. Returning from a viewer or completing an action requests fresh data and discards any read started before the transition. Runs the dashboard starts are ordinary `cones run` subprocesses and appear in the ledger.

## Polling

Nothing tells the dashboard that a session changed. Claude writes its registry entry, a background job's state.json and the transcript; Codex writes its rollout and holds its locks; cones has no hook in either harness, no process inside a session and no socket it listens on, by the first rule of [AGENTS.md](../AGENTS.md). So the dashboard asks, again and again, and every cell is what the harness's files said the last time it asked. The policy has four parts.

**One read a second, on its own thread.** A read starts when a second has passed since the last one landed, never while one is in flight, so a slow read stretches the cadence rather than piling up. The loop that draws the frame checks for the landed read every 25 ms (every 8 ms while a viewer is focused, so typing into it feels direct), lands it, pumps the viewers' ptys and redraws only when something changed; the spinner ticks on its own 100 ms clock. Returning from a viewer, finishing a stop or a delete, or `ctrl+r`, invalidates: a read already in flight is thrown away when it lands and a fresh one starts, so the row never shows a snapshot older than the transition. A change the harness wrote reaches the screen within a second plus one read.

**A read touches everything, once.** The ledger for runs, hidden runs and pinned folders; jobs.yaml; every `~/.claude/sessions/<pid>.json`; one `ps` for all of those pids at once, since a pid whose start time is not the entry's `procStart` is not a session; each background job's state.json; the statusLine sidecar; and for Codex the process table, the daemon's open files and the threads table of its sqlite state, read whole each time. On this machine, with eight live Claude sessions and transcripts up to 20 MiB, a read takes about 100 ms and the slowest one in 300 took 700 ms; `cones tui --debug` logs each as `refresh_read` and a discarded one as `refresh_discard`.

**Transcripts are read by length.** A transcript's title, last reply, start, activity, model, context and tokens are cached against the file's length; a transcript that did not grow costs a `stat`. One that grew is read again in full, line by line, since tokens are a sum over every message and a message can be repeated across lines. The title and the last reply are read from the end in windows that start at 256 KiB and grow fourfold to 16 MiB, so a long session costs about what a short one does. The pane's preview of a transcript is re-read only when the file grows too. Codex's rollout header is cached for good, since it never changes once written; its first prompt is cached once found. A rollout's tail is folded, not re-read: the whole file once, then only the bytes appended since, so a `task_started` a megabyte of tool output ago still makes the row active, and a half-written last line waits for its newline.

**Nothing is deduced from time.** No mtime, no `updatedAt`, no "quiet for a minute means idle": the state is the word the harness wrote, and a harness that writes late shows late. Claude flips the registry to `busy` the moment a prompt is sent but rewrites a finished job's state.json only with its first progress note, tens of seconds later; until 2026-09-15 the job file was read first, so a row stayed `done` for that long after a new prompt. The registry's `busy` now comes first, and `done`, `failed` and `stopped` still beat an idle registry. If a row lags, find which file the harness wrote late before changing the cadence: a faster poll cannot show a word that is not on disk yet.

A file watcher was not chosen. The files are in three trees, transcripts grow continuously while a session works, so a watcher would fire as often as the poll reads, and a poll that finds nothing changed costs a directory listing and a few `stat`s.

## The screen

| Pane | Columns |
| --- | --- |
| Menu | `runs`, `agents`, `folder`, `help`: one row of buttons above the tables, described under [the menu](#the-menu) |
| Jobs | enabled marker, name, schedule, harness, on/off, last run status |
| Sessions | icon, harness, `orchestrator` on the folder's coordinator and `own terminal` on a session that cannot be joined from here (blank otherwise), title or short id, then the `columns:` list from jobs.yaml, described under [columns](#columns) |
| Runs (newest 200) | icon, job, status, fired time, duration, dollars, reason |
| Viewer | the selected or focused session's live screen, on a terminal at least 140 columns wide |

There is no details pane for now; a session is read by opening it, a run by `cones logs`. `cones ls --json` still carries what the pane showed, so it can come back.

Each table opens with a dim row naming its columns, padded to the table beneath. A column only grows for the life of the dashboard: a cell that changes length (`59s` to `1m`, `working` to `needs input`, a long title leaving) never moves the columns beside it, so a column that was once wide stays wide until the dashboard restarts. The cursor skips the naming row and `/` hides it while a filter is set. The sessions row sits once above the first directory group, since the groups share one table.

Sessions group by directory like Claude's own agents view, or by state so the rows that need a human are on top. A folder the menu's `folder` prompt picked keeps a group of its own after the session groups, with one dim row while nothing runs there, until `ctrl+x` twice removes it; the folders are one path per line in `~/.cones/folders`. Within a group they are ordered oldest first by start time, so a new session appends at the bottom and rows hold still; a session whose transcript reports no start sorts last, by id.

| State | Label | Color |
| --- | --- | --- |
| `done`, `failed`, `stopped` | the word itself | green, red, dim |
| `active` | working | plain |
| `blocked` | needs input | yellow |
| `idle` | idle | dim |
| anything else | the word itself | red |

Working is plain and green is kept for finished work, as in Claude's own agents view. Which harness fact each state comes from is the State row in [harness.md](harness.md#observe). The folder's coordinator says `orchestrator` and its title is orange, as [coordinator.md](coordinator.md) describes.

Under the composer, the hint line names only the keys that act on the selected row, then the ones that act everywhere: `enter <verb> · ctrl+x <stop|delete|hide|forget> · ctrl+e edit · tab <harness> · ctrl+n new job · ctrl+s regroup · ctrl+o agents · ctrl+g guide · esc quit`. The verb is `start job` on a job, `follow log` on a running run, `attach` on a session or a finished run, `return` on a row whose viewer is alive inside the dashboard and `own terminal` on a session that cannot be joined from here; `ctrl+x` reads `delete` on a job with no run in flight, `forget` on a Codex daemon thread, `hide` on a finished run and `delete` on a Claude background session, which `claude rm` removes from `claude agents` as well; `ctrl+e` shows on a job only; on the menu row the verb is the picked button's, `new job`, `agents`, `pick folder` or `guide`, with `← → pick` beside it, and on a pinned folder's row `start here`, with `ctrl+x` reading `remove`. With an instruction typed it reads `enter start <harness> in <dir> · tab <harness> · ctrl+v paste image · esc clear`, or `enter run once in <dir>` on the menu's `runs` row. The last action's status takes the line until the next key. On a list column too narrow for every key, the keys that act everywhere go, last first, while the selected row's key and `esc quit` stay.

## Columns

`columns` in jobs.yaml picks what a session row shows after its icon, harness and title. Order is kept. An unknown name fails validation, so a column cones cannot fill never renders as a dash. Each cell reads one line the harness wrote, named in the Observe table of [harness.md](harness.md#observe); it is `-` until that line exists, never an estimate.

| Column | Cell | Default |
| --- | --- | --- |
| `state` | working, needs input, idle, done, failed or stopped, as in the table above | yes |
| `model` | The bare API model id on the last message with usage, `claude-fable-5-1` or `openai.gpt-6-astra` | yes |
| `age` | Time since the transcript's first timestamp, `4s`, `6m`, `2h` | no |
| `activity` | Time since the transcript's last timestamp | yes |
| `context` | `98k/200k`: the prompt size the harness reported on the last message over the window it stated; `98k` alone when nothing stated a window (a Claude session whose statusLine command does not save its payload) | yes |
| `last` | First line of the last reply, or the directory when grouped by state | yes |
| `tokens` | `49.2M/201k`: input and output tokens summed over the session | no |

`age` counts from the transcript's first timestamp and `activity` from its last; neither reads the registry's `updatedAt` or the file's mtime, so a session that is idle shows a growing `activity` and a fixed `age`. Cost is not a column: the harnesses write tokens to the transcript and no price, so live sessions have no dollars to show. Run rows take theirs from the ledger.

The first press marks the row red and stays armed until the second press; any other key keeps it. |

| `ctrl+e` | With the composer empty, edit the selected job in the same wizard, filled in from the file; with an instruction typed it is end of line, as cmd+→ arrives. |
| `ctrl+s` | Regroup sessions by state or by directory. |
| `ctrl+o` | Open a harness's own agents view without picking a row first: `claude agents`, or Codex's `resume` picker as a client of its app-server daemon, so a thread picked there keeps working when the client is left. `←` `→` pick the harness, `enter` opens, `esc` cancels. `esc` in Claude's agents view quits it and comes back here (`q` types into its prompt); Ctrl+Z comes back too and leaves the view running, so `ctrl+o` then `enter` on that harness returns to it. Its keys cannot be rebound to do this: Claude's `Agents` keybinding context accepts only its own two actions, and `~/.claude/keybindings.json` is global, not per launch. |
| `ctrl+f` | Filter rows by text; `enter` keeps the filter, `esc` clears it. A kept filter shows at the left of the hint line. |
| `ctrl+\` | Inside a viewer on a terminal at least 140 columns wide, pick the layout: the viewer beside the list, or over the whole frame with the strip under it. A layout, not a state: it stays across Ctrl+Z and `enter` until pressed again, and the strip under a full-frame viewer offers the split back. On a narrower terminal the key changes nothing and the hint line says `split needs 140 columns`. From the list the key does nothing. Never forwarded to a viewer. The terminal sends it as the byte 0x1c, the same byte as ctrl+4, so the dashboard takes both spellings. ## Viewers

A session, a finished run or an agents view opens as a viewer. The agent is never in the dashboard: it runs in its harness's daemon, and the viewer is that harness's own client of it, `claude attach` for a Claude background session, the Codex TUI as a `--remote` client of the app-server for a Codex thread; [harness.md](harness.md#kinds) says which client each kind gets and why an agent that owns a terminal elsewhere gets none. The client runs on a pty the dashboard owns, sized to the pane, and what it writes goes to a vt100 emulator whose screen the dashboard draws as part of its own frame. So the shell never shows, not while the client starts and not while it shuts down; no mode a client turns on (mouse reports, bracketed paste, focus events) is left on the terminal, since it was never on it; and leaving is a focus change, the client parsing off-screen until `enter` returns to its current screen. Nothing here parks a harness with SIGSTOP: a viewer that stops itself is closed, and where a harness cannot be left and re-entered the dashboard says so and does not open it.

Being the client's terminal, the dashboard answers its queries itself: cursor position, device attributes, and the default foreground and background colors, probed from the real terminal once at start, so a client picks the same light or dark theme it would in a shell. The kitty keyboard query it leaves unanswered on purpose: Claude and Codex both fall back to the classic xterm encoding, which is what the dashboard sends them, so chords that encoding cannot express, shift+enter among them, arrive as their plain key. Answering would mean encoding every key the kitty way in `src/viewer.rs`, the change to make if that ever matters. A frame a client brackets in synchronized output (Codex draws every frame that way) is shown whole: the pane keeps the previous frame, cursor included, until the update ends, or for 150 ms if it never does.

Ctrl+Z never suspends the dashboard. It is a focus change: the dashboard takes the frame back and redraws at once, the viewer stays alive off-screen, and `enter` on its row returns to its current screen in one frame, with no second `claude attach` start to wait for. While the cursor rests on a Claude background session row, 150 ms beside the list where the pane waits for it and 400 ms elsewhere, its viewer opens out of sight, so `enter` shows it at once; only those rows are opened this way, since joining one changes nothing in the fleet, while resuming a finished run or opening a Codex client would show there, and until `enter` has been on it the hint line still reads `attach`. The three most recently used viewers are kept; when a fourth opens, the least recently focused closes; viewers opened by a resting cursor have a pool of three of their own beside them, the oldest closing first, so rows the cursor visited lately show at once however many viewers are live; `ctrl+x` confirmed on a row closes its viewer first; every viewer closes with the dashboard. The session a viewer showed is untouched in every case.

On a terminal at least 140 columns wide the frame is two columns: the list on the left, half the width within 60 to 100 columns, a rule, and a pane with the rest. The pane draws the focused viewer, else the selected row's viewer; on any other session row nothing of another session, so a Codex row never has a Claude screen under its name; on a row that is not a session, the viewer focused last, never a harness's agents view: leaving `claude agents` with `ctrl+z` shows the agent seen before it. Until a viewer has painted, and on any session row that has a transcript but no viewer of its own, the pane shows the last assistant headlines of that transcript, dim, one per line after `· `, read again only when the file grows, so a row shows something the moment the cursor lands on it; with nothing to show it says what `enter` does. `enter` or a click on the pane focuses its viewer, which changes only where the keys go: the rule turns orange, the composer's block cursor gives way to the viewer's, and the hint line reads `ctrl+z back · ctrl+\ full screen`, with the filter in front as always. `ctrl+\` there picks the full-frame layout instead, the viewer over the whole frame with the strip under it, and the layout stays until `ctrl+\` again; `shift+enter` on the row is both at once, focus in the full frame (Claude Code's terminal bindings send it as `ESC CR`, alt+enter to the dashboard, which counts the same); in it a wide terminal shows the list alone while nothing is focused. On a narrower terminal that is the only layout, and while a viewer is focused the frame's last row is the dashboard's strip, as a tmux status bar sits under a pane: the cone, the viewer's name (its own window title, else its row's title), the same fleet counts the header shows, and the keys that leave. The counts stay live, and when a session other than the one shown needs input the strip says so in yellow with that session's title, so a prompt waiting in one session is seen from inside another.

Inside a viewer every key is the viewer's except Ctrl+Z and `ctrl+\`. Pasted text arrives as one paste; an empty paste, cmd+v over an image in VS Code, arrives as ctrl+v, the harness's own image paste. The mouse works inside the pane, and beside the list it is read with nothing focused too: a click on the pane focuses its viewer, and a click on a list row selects it and takes the keys back. The terminal's own text selection therefore needs its modifier while the pane is on, option-drag in iTerm2. The wheel over the pane scrolls its viewer, focused or not: a viewer that reads the mouse gets the wheel itself, and one that does not (Codex leaves scrolling to the terminal, as a shell does) scrolls the emulated screen back through the last 1000 lines that left its top, as does shift with the wheel or shift+pgup/pgdn inside a viewer; a key typed into the viewer brings it back to the bottom.

Opening a session runs `claude attach <short id>` from the dashboard itself; a finished run goes through `cones attach`, which resumes it. A Codex client needs the daemon's socket first, so the command is prepared on a thread with `opening codex` in the hint line; `esc` cancels it and the instruction stays in the composer, and the address is kept and probed, so the second open does not start the CLI again. On return the dashboard reloads and finds the row again by its id, so a session that went from idle to working while it was open, and so moved to another group, is still the selected row. A session that ended while open leaves the cursor on its neighbor.

For intermittent delays, `cones tui --debug` writes timings to `STATE_DIR/tui-debug.log` (the lines are listed in [cli.md](cli.md)) and `scripts/bench-tui.py` summarizes that log or measures the real TUI against fixture harnesses; its header says how.

## The menu

One row of buttons sits above the tables: `runs`, `agents`, `folder`, `help`. A fresh dashboard opens on the first table, and `↑` from there lands on the row; `←` `→` pick a button, a click picks the one under the pointer, and only the picked one shows what it does, dim beside the row. `enter` presses it. `help` opens the guide, the same as `ctrl+g`. The others act on the menu's folder: the directory the dashboard was started in until `folder` picks another, so work can start in a directory nothing runs in yet. `runs` turns the composer into a supervised one-off run: type an instruction and `enter` starts `cones run --prompt` with it in that folder, under the first job's policy, in the ledger like any other run; with nothing typed, `enter` opens the job wizard, the same as `ctrl+n`. `agents` opens the same harness picker as `ctrl+o`. `folder` asks for a directory on the prompt line, relative to the current folder with `~` expanded; `tab` completes it as a shell completes `cd`: one match fills in with a trailing `/`, several fill in what they share and a second `tab` lists them on the hint line, and hidden folders are offered only after a `.`; a path that is not a directory is refused on the hint line and the prompt stays. The `folder` row names the folder, and the composer on any menu row starts its session there. The folder taken also gets a row of its own in the sessions table, whether or not anything runs there, so the place is on screen from the moment it is picked; the row stays across restarts until `ctrl+x` twice on it removes the folder, and a session starting there takes its group over. With the row selected the composer starts its session in that folder, and the hint line's `ctrl+x` reads `remove`.

## The composer

Above the hint line is a composer drawn like Claude Code's own input: ruled above and below, with a block cursor on the character the next key acts on, after what is typed when nothing follows it, or on the first letter of the placeholder, and it is three rows tall, one of text between the rules, until an instruction outruns the width; then it wraps and grows a line at a time (up to eight), so nothing typed is cut off. Its prefix is the harness `tab` picked; type an instruction and `enter` starts a session with it in the selected row's directory (a job's `cwd`, a session's, a run's), or the menu's folder from a menu row, so starting work never depends on a session already being there. Claude starts as a background session (`claude --bg` with the instruction) on a thread, so the dashboard never waits; its row is there the moment `enter` is pressed, working, titled with the instruction's first line, and the registry's row takes over once Claude lists the id `--bg` printed. Until then `enter` and `ctrl+x` on it say it is still starting; a launch that fails takes the row away and puts the instruction back in the composer. Once listed, `enter` on the row attaches and Ctrl+Z comes back. Codex has no background mode, so it opens here as a thread of its app-server daemon with the TUI as a client, as [harness.md](harness.md#kinds) describes; leaving the client keeps the thread and the dashboard records its id to resume it. A harness that cannot be left running is refused with the reason on the hint line and the instruction stays in the composer. There is no policy and no ledger here: it is the harness natively in that directory, with its own permission prompts. A supervised one-off run is the menu's `runs` row, or `cones run --prompt` from a shell.

Under the composer, the hint line names the keys, or shows the last action's result until the next key.

## The job wizard

Jobs are added, edited and deleted from the dashboard; the file stays yours to edit by hand too. `ctrl+n`, or `enter` on the menu's `runs` row, asks four questions on the prompt line, each answered with `enter`; backspace on an empty answer goes back one, `esc` cancels.

| Question | Answer |
| --- | --- |
| `name ›` | 1-80 letters, digits, `-` or `_`; the launchd label is `local.cones.<name>`. |
| `dir ›` | A directory. `~` expands, a relative path is taken from the jobs file's directory, and the placeholder is the selected row's directory, or the dashboard's cwd with nothing selected; `enter` on an empty answer takes it. `tab` completes it as the `folder` prompt does. A path that is not an existing directory stays on the question with `not a directory: /path` inline. Stored in `~` form. |
| `schedule ›` | Five-field local-time cron, as in `0 9 * * 1-5`, checked the way `cones install` checks it. |
| `prompt ›` | The task. |

The job is a Claude job under the file's defaults; model, budget, tools and the rest are edited in the file, see [jobs.md](jobs.md). Saving rewrites only that job's block of jobs.yaml, found by its `- name:` line, so comments elsewhere and the other jobs' formatting survive; the whole file is validated first and a bad answer comes back inline with the file untouched. `ctrl+e` on a job row opens the same wizard filled in from the file, and saving keeps every field the wizard does not ask about. `ctrl+x` twice on a job with no run in flight removes its block. After each of these the dashboard runs `cones install`, so launchd matches the file; an install error shows on the hint line.
